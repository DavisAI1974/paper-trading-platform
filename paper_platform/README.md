# Purchased MBO paper platform

The registered market is NYMEX Henry Hub natural gas futures. Its input is the already-purchased daily DBN archive in `DavisAI1974/markets-data`. The purchased replay uses the existing archive. Live capture is a separate, manually selected data input. The 30 versioned rules are in `rules/`. CL decisions use the exchange event boundary specified by the rule. CX print-pair decisions use the next print in tape order. A management action names its originating trade and rule. Each manager has its own record of what it would do at that entry.

## Market configuration and display

`markets/nymex-ng.json` selects the archive, instrument, adapter, price units and rules. The HTML template in `monitor.html` is shared. Another market needs its instrument definition and applicable feed, book, calendar and strategy logic. Options also need expiry, strike, call or put, underlying and multiplier. Add the profile when those inputs have been verified.

The Render service serves the HTML and read API. Server-sent events update an open page. The browser reads the initial view and rule definitions with JavaScript disabled. The API exposes `/api/markets`, `/api/rules`, `/api/session` and `/api/events`. Select a strategy to see one row per trade across the selected run. Each row shows the entry and exit in Eastern time to the nanosecond, both quotes and the recorded reasons. Manager exits identify their parent entry. Forced closes carry their administrative label. `/api/trades?rule=CL01&run=<run>` returns the paired journal orders for that rule. Events support market, run, rule and sequence filters. Use `follow=true` for the live NDJSON stream. Nanosecond values outside JavaScript's safe integer range use decimal strings. A local controller can use `api.application(session)` to step a separately authorized session with its expected cursor.

## Replay and evidence

ROOT's archive reader checks file hashes and record counts. NautilusTrader maintains the L3 order book that supplies strategy bids and asks. ROOT supplies the exchange queue rules and the source history for individual orders. At each later UTC file's restatement the reader compares the carried order IDs, FIFO order and remaining quantities before accepting further records. A fresh session rebuilds the book from Sunday, checks each later opening restatement and retains the raw record's file hash and zero-based index. The original compressed bytes stay in the purchased input archive. The receive-time sidecar holds one little-endian unsigned 64-bit replay-host nanosecond timestamp per delivered record in that same order. Signals use historical receive time. The replay host's clock controls pacing and run duration.

Only a named trade day's records reach the strategy adapter. The existing research ROOT gate remains intact. Each trade record retains both quotes when available. The ledger records unpriced paper orders. An authorized workflow takes Frankie’s or the agents’ execution instructions. With an execution plan, journal fills come from the Nautilus L3 matching engine. Each forced closing order carries its stop reason and `trade_data=false`. There is no research P&L.

## MBO capture

`python -m paper_platform.record_mbo` records data into a Linux checkout of `DavisAI1974/markets-data`. Its required arguments are `--data`, `--trade-day`, `--source purchased|live`, `--message-budget` and `--greg-go`. The purchased source reads the manifest-listed DBN files from the Sunday start through the named trade day. The live source subscribes to GLBX.MDP3 MBO for NG.v.0 using the account's existing Databento entitlement and the `DATABENTO_API_KEY` environment variable. It requests the week from Sunday UTC. The paper replay workflow keeps its existing input.

The recorder writes `paper-trading/captures/nymex-ng/<sunday>/<source>.sqlite`. It commits each metadata block, MBO record and control record with the time the recorder received it. Purchased input retains each decompressed DBN frame. Live input retains the DBN bytes the pinned Databento client delivers to its output stream. Each connection has its own start, end and status. A hard interruption can leave the end time unknown.

Restarting a source for the same week records a new connection. The recorder compares each replayed MBO record byte for byte with the committed position before it appends new positions. Repeated deliveries retain their new receive times and point to their original tape positions. UTC-file opening restatements from purchased files remain in the delivery journal. The recorder uses the existing Pushover configuration for its stop, budget and failure notices. The delivery budget includes replayed records and control messages. Extending an existing capture requires a budget large enough to reach past its committed prefix.

`CapturedFeed(path, trade_day).messages()` reads the committed tape. With `follow=True` it tails new positions while the recorder is active. It seats the book at the Sunday clear, carries it across UTC midnight and produces strategy inputs with the same `MboTape` code as purchased replay. Each decision source reference uses the SHA-256 of the captured MBO frame and its tape position. The recorder produces no strategy orders. The live paper workflow runs the recorder and the paper runner side by side. The capture workflow restores encrypted checkpoints from markets-data and publishes new ones each minute and at shutdown. A hard host loss can lose original host timestamps since the last successful checkpoint. Recovery on a replacement host still needs evidence.

## Operation

Before recording a session, the runner replays a prefix of the selected market and trade day twice. Both passes seat an independent order book from Sunday. One can read the full archive through the cutoff. The other receives a copy ending at the exact source record. The runner compares the ordered decisions, including observations and the source cursor of each batch. The default sample covers 4,096 eligible records and extends in search of an opening when needed. The receipt identifies the cutoff, decision count and digest. A mismatch blocks the session. The preflight counts toward the runner's wall-clock limit.

The named NG trade day opens at 6 p.m. New York time the evening before and closes at 5 p.m. on its named date. The 5–6 p.m. break is recorded separately. A UTC file boundary leaves the book in place.

The CL07 and CL08 timer can close a position between tape messages. Its record includes the expiry nanosecond, the expiring source records and the source of the last known bid and ask. CL01 records whether a qualifying third step occurred before the reversal. CX interruptions and missing inputs end the affected assessment. The ledger tracks positions that still need an administrative close. The phone page and API carry the subsequent prints and quotes observed under the saved CX rules.

The supplied Actions workflow accepts Greg's manual approval, market, named trade day, message budget and event budget. An atomic signal/order batch that would exceed the event budget ends the run before that batch is published. Administrative close and receipt records are always written. The clock limit is 5.75 hours. Each run writes a new directory on its own `paper-runs/<run>` branch in markets-data. Git publishes on paper orders, each minute and at shutdown. The Actions data repository is public at the time of this build. A password on the viewer only protects the viewer.

The proposed host is Render using `paper_platform/render.yaml`. The proposed phone service is Pushover. Both require setup before an operational run. The runner expects `PAPER_RELAY_URL`, `PAPER_RELAY_TOKEN`, `PUSHOVER_APP_TOKEN` and `PUSHOVER_USER_KEY`. The paper workflow uses `MARKETS_DATA_DEPLOY_KEY` to publish receipts. Its public key is a write-enabled deploy key on `DavisAI1974/markets-data`. Select `verify_writer` on the verification workflow to check access with a dry-run push. HTTPS checkouts can also use a `MARKETS_DATA_TOKEN` scoped to writing the data repository. The viewer also needs `PAPER_VIEW_PASSWORD`. Set values in the service secret stores. Render's SQLite cache is ephemeral. The events in markets-data are the permanent record. Hard termination of the runner can prevent application finalizers and phone delivery.

## Local verification

Set `MARKETS_DATA` to a checkout containing `data/nymex_mbo/ng_v0_oct2023/MANIFEST.json` and its purchased files. Run `python -B -m pytest -p no:cacheprovider paper_platform`. The tests check field preservation, the Sunday-to-Monday boundary, the signed-trade flow calculations, the physically truncated tape prefix and the HTML/event API using a real decision. These tests do not authorize a platform run.

## Agent execution plans

Frankie and the Ccode-managed agents own order placement and contract size. All 30 research rules remain in the catalogue. The manual workflow accepts an execution plan as JSON. Supply the real NG contract's Nautilus `FuturesContract.to_dict()` representation in `instrument`, the corresponding numeric `databento_instrument_id`, and a `rules` mapping keyed by catalogue ID. Each participating rule supplies a positive integer `contracts` plus `open` and `close` instructions. The supported instructions are `post`, `cross`, and `cross_limit`. Plans can also specify a tick offset on each posted or price-capped leg. Both workflows accept a filename from [`execution_plans`](execution_plans/README.md) or an inline plan. Unselected rules still publish their research observations. Managers can follow entry signals named by their agents, with independent orders, fills and inventory.

Each participating strategy has an independent native L3 matching engine. A posted buy joins the bid, a posted sell joins the offer, and crossing orders consume displayed liquidity. The engine handles partial fills and reports maker or taker status. An exit cancels outstanding orders for the trade and uses the filled quantity. Administrative liquidation records any remainder the available book could not absorb. A paper fill is a simulated execution based on observable MBO. The research record continues to carry both quotes separately.

The replay workflow defaults to the pinned purchased MBO archive. Selecting purchased-capture or live-capture restores the encrypted weekly checkpoint from markets-data. Stored captures advance in tape order through the same session and finish at the earlier of EOF and the end of the named trade day’s final UTC file. The receipt identifies the checkpoint commit. A stored replay starts fresh at the named trade day. A live session also warms through any history already available at its manual start. For a completed live run, select live-capture and enter its original run ID in the replay workflow. Choose a platform branch or tag whose history contains the live run commit. The workflow runs the original revision in a detached checkout and installs its declared requirements. Leave the execution plan blank to use the original agent plan. The receipt must contain the first live decision cursor (which may be null if the runner only warmed history). Replay uses the recorded eligibility boundary and stops at the last MBO the original runner processed, even if more frames reached the recorder. The original and replay runs have separate IDs and journals. The supplied budgets can end the replay earlier.

The separate live workflow requires Greg's go, a live data entitlement, the same agent plan, and both budgets. A weekly replay-complete message marks the transition into live delivery. Captured history warms the engine before new orders become eligible. The session receipt includes its plan and causal cutoff. No workflow runs on a push or a pull request.

Capture recovery uses a dedicated markets-data branch per source and week. Set `PAPER_CAPTURE_KEY` to a Fernet key in the platform repository's Actions secrets and keep a recoverable copy in the owner's secret store. Existing checkpoints require that same key. Live capture also needs `DATABENTO_API_KEY`. Render needs the viewer password and relay token, and Actions needs the matching relay token and Render URL. The htmx library is bundled with the HTML dashboard.

## Recovering the phone view

The [dashboard restore workflow](../.github/workflows/restore_phone_dashboard.yml) accepts the ID of a completed run. It reads the journal and receipt on that run's markets-data branch and sends the original sequenced events to Render in transactional batches. Duplicate deliveries preserve the original event. A sequence collision rolls back the batch. The last event restores the recorded stop reason. The restore command only uses the relay ingest API.


## Feed interruptions during a live paper run

The live workflow binds the paper runner to the connection opened by its own recorder. A Databento error, disconnect, heartbeat timeout or checkpoint publisher failure stops that session. A writer that exits abruptly can leave its end time unknown. The reader detects the released writer lock and reports the abrupt exit.

For a feed failure the runner cancels resting paper orders, retains any filled contracts still held, and records that liquidation was unavailable. Normal budget and clock stops retain their administrative liquidation path. The terminal journal event and receipt distinguish the recorder’s last durable MBO position from the runner’s last processed input. The Render dashboard shows both when available, including when viewing a single strategy or restoring a completed journal. Pushover stop notices carry the two positions when the runner receives the recorder’s terminal record.
